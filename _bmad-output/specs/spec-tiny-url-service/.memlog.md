- (capability) CAP-1 Merchant can mint a tiny URL from a long destination URL copied from their order site
- (capability) CAP-2 Customer with a tiny URL reaches the exact original long URL the merchant submitted
- (capability) CAP-3 Same sanitized long URL always returns the same existing tiny URL (idempotent)
- (capability) CAP-4 Long URL must pass an HTTP liveness check (success, redirects count) before anything is stored
- (capability) CAP-5 On create success, merchant sees the tiny URL and the bound original long URL; the tiny URL itself carries no destination payload
- (constraint) Sanitize long URL before existence check so messy duplicates collapse
- (constraint) Create path is atomic: check-then-bind or return existing; no partial wrong binding under concurrent creates
- (constraint) Stored destination is the original merchant-pasted long URL, not a post-redirect final URL
- (constraint) Mappings are persistent; tiny URLs remain unique across different long URLs
- (constraint) Client error responses such as 404 fail the liveness gate and nothing is stored
- (decision) Why: opportunity+pain — merchant needs a seamless digital address so customers reach a complex order destination without handling the long URL
- (decision) Non-goals: no order-domain intelligence; no merchant order site; no encoding destination data into the short form; no analytics/vanity/auth/TTL unless later decided
- (assumption) HTTP 2xx after following redirects counts as success for liveness
- (assumption) Service is destination-agnostic: it stores and resolves URLs, not order objects
- (question) How should timeouts and 5xx on the liveness check be treated?
- (question) Is create authenticated, or open to anyone who can call the API?
- (question) Do tiny URLs expire, or persist indefinitely?
- (question) Are custom/vanity short forms in scope?
- (decision) Companion create-pipeline.md holds ordered create steps: sanitize, liveness, lookup, atomic bind
